项目背景与问题背景

项目背景

当前 AI Coding 平台积累了大量会话轨迹，但经验难以跨用户、跨时间复用。

静态 Skill 也跟不上新工具和新失败模式的增长，因此 SkillClaw 关注从交互中持续进化 Skill。

核心关注：如何把使用过程中反复出现的经验，转化为可复用、可验证、可部署的技能改进。

问题背景

  • 用户从中心化技能市场安装 Skill，技能由人工维护。
  • 正确参数、调用顺序、错误处理只停留在当前会话。
  • 不同用户在相同失败模式上重复试错。
  • 系统级知识无法累积，每个用户都在重新摸索。
本质矛盾：用户操作在重叠任务空间中，系统却没有利用这些反复出现的经验来改进自身。

论文要解决的 3 个问题

证据聚合

如何把分散、异构的用户交互会话，转成可用于跨用户推理的结构化证据？

进化机制

如何自动诊断技能的成功模式和失败根因，并生成合理的 Skill 更新？

质量保证

如何确保更新是单调改进，只接纳真正提升，而不破坏已有有效行为？

核心创新：把 Skill 进化做成系统闭环

1

集体进化框架

首次在多用户 Agent 生态层面实现技能的集体进化。不同用户的交互轨迹被聚合为共享证据库，一个用户发现的改进可以传播给所有用户，形成系统级的知识积累。
2

Agentic Evolver（智能进化体）

技能更新由一个自主 LLM Agent 通过开放式推理完成，而非预定义规则。进化体可以诊断根因、选择动作（改进 / 创建 / 跳过）、并直接编辑技能定义，能够处理未见过的失败模式。
3

按技能分组的证据机制

会话按引用的技能分组后，同一个技能在不同用户、任务、环境下的表现差异天然形成对照实验，直接揭示技能在哪里有效、在哪里失效。无技能会话组则用来发现潜在的新技能缺口。
4

验证驱动的单调部署

候选技能更新在夜间同环境下与当前最佳版本对比验证，只有表现更优才被接纳部署，保证技能池单调不退化。

Session 更新 Skill 池的总表达

给定当前共享 Skill 集合和一批新产生的用户会话，系统输出更新后的 Skill 集合。

S′ = Φ(S, T)

S：当前共享 Skill 集合。

T：多用户交互产生的 session / trajectory 集合。

Φ：由 Agentic Evolver 完成的证据分析、Skill 提取、Skill 进化与验证过程。

多数 Skill 缺陷是过程错误

  • 工具参数或 API 地址错误。
  • 操作步骤顺序不正确。
  • 缺少输入、环境或输出检查。
  • 工具失败后进行无效重试。
  • 最终结果正确，但过程不稳定或成本过高。

会话聚合与 Skill 归属

会话不会只作为孤立样本存在，而是根据其中实际引用、读取或修改过的 Skill，被放入对应的证据组。这样，同一个 Skill 在不同用户、任务和环境下的表现差异，就能被放在一起比较。

形式化表示

G(s) = { τᵢ | s ∈ Kᵢ }

Kᵢ：会话 τᵢ 实际引用的 Skill 集合。

G(s)：某个 Skill s 对应的会话证据组。

A
引用 Skill A 的会话进入 G(A)。
A + B
同时引用 A、B 的会话会同时进入两个组。
empty
未引用任何 Skill 的会话进入 G(empty)，用于发现潜在新 Skill 缺口。

成功样本

帮助确认当前 Skill 哪些行为应该保留。

失败样本

Skill 进化：成功与失败共同塑形

s′ = φ(s, Gsuccess(s), Gfailure(s))

成功会话

定义应该保留的不变量，避免改坏已经有效的行为。

失败会话

定义需要修正的流程、参数、环境检查或适用边界。

不稳定会话

揭示 Skill 在哪些任务、上下文或工具环境下不可靠。

动作含义适用场景
Refine修正或增强现有 Skill已有 Skill 有价值，但存在重复失败模式。
Create创建现有 Skill 未覆盖的新能力无 Skill 会话中出现清晰可复用程序。
Skip证据不足，保持现状改动风险大、模式不稳定或收益未验证。

Evolver 的工作方式

1
读取结构化会话、当前 Skill 和历史版本。
2
比较成功、失败和工具错误模式。
3
判断证据是否跨会话重复出现。
4
选择 Refine、Create 或 Skip。
5
生成候选 Skill，记录版本证据和修改理由。
约束框架限定输入、输出和动作；LLM Agent 负责诊断具体失败模式。

任务环境

完整 Linux 工具环境，覆盖文本、代码、图像和视频等多模态输入。

评分方式

每个任务由 3-7 个指标聚合评分，关键约束违反可能直接记为 0 分。

运行节奏

白天执行任务，夜间聚合会话、生成候选并验证；第 1 天是基线。

结果解释

局限性与开放问题

项目隔离

不同项目的同名 Skill 可能在同一共享组内聚合，造成经验污染。

使用记录缺失

会话归属依赖 Skill 读取或修改记录，客户端上报不完整会导致误判。

多 Skill 归因

一个会话调用多个 Skill 时，成功或失败可能归因给无关 Skill。

聚类质量

无 Skill 会话场景差异大时，系统难以发现统一模式。

反馈与评分

候选判断依赖反馈和评分，可能错误跳过或错误接纳。

数据治理

会话可能包含源码、内部路径、账号和业务知识，需要脱敏、权限和审计。

总结：SkillClaw 到底贡献了什么

  1. 保存能反映因果过程的完整 Agent 轨迹。
  2. 按 Skill 使用关系聚合跨会话证据。
  3. 从无 Skill 会话中发现可复用的新程序。
  4. 联合成功和失败轨迹优化已有 Skill。
  5. 通过同环境验证决定候选是否进入最佳技能池。

SkillClaw 的关键不是让 Skill “自动变多”，而是让 Skill 的变化有证据、有验证、有边界。

这也是它对 Agent 长期学习系统最值得借鉴的地方。
